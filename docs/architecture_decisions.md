# 架构决策记录

本文档记录“企业知识库 RAG + AI Agent 平台”的关键技术取舍，帮助面试官理解当前实现为什么这样设计，以及后续如何生产化升级。

## ADR-001：使用 FastAPI 作为后端框架

**决策：** 后端使用 FastAPI 承载认证、文档、问答、Agent、评测、审计和 dashboard 接口。

**原因：**

- Python 生态适合 AI 应用开发。
- FastAPI 对 Pydantic、OpenAPI 和异步接口支持较好。
- 面试中容易展示接口设计、依赖注入、测试和后续模型接入。

**取舍：** 当前项目更重视 AI 应用闭环和本地可运行性，没有引入复杂微服务拆分。生产环境可以按业务边界拆分文档处理、检索、Agent 执行和评测任务。

## ADR-002：使用 SQLite 支撑本地演示

**决策：** 当前版本使用 SQLite 存储用户、文档、片段、问答日志、Agent 运行和评测记录。

**原因：**

- 零外部依赖，适合 GitHub 作品集、毕业设计演示和面试快速复现。
- 一键启动成本低，不需要先安装 PostgreSQL 或 Redis。
- 表结构仍能体现企业知识库系统的基本数据建模能力。

**取舍：** SQLite 不适合作为多人生产环境数据库。生产化路径是迁移到 PostgreSQL，并配合迁移工具、连接池、备份和权限策略。

## ADR-003：使用可降级的混合检索

**决策：** 默认使用字段加权 BM25 + 本地重排，其中正文占 70%、标题占 30%；显式配置 Embedding 后，文档入库会持久化向量，查询时融合 BM25 和向量相似度。历史文档支持批量补建向量。

**原因：**

- 未配置外部服务时仍可离线运行，不依赖 Embedding API。
- 字段加权 BM25、向量和重排分数分别保留，便于排查召回和排序问题。
- Embedding 模型必须显式配置，不硬编码会过期的模型名称。

**取舍：** 默认向量仍保存在 SQLite JSON 中，保证零服务启动；可选 pgvector 后端使用 HNSW 和连接池承担向量 Top-K，并保留 SQLite 降级副本。关键词 BM25 目前仍在应用内计算，下一步可迁移到 PostgreSQL 全文检索或独立检索服务，并使用独立 rerank 模型。

## ADR-004：Agent 工具调用使用可控工具链

**决策：** Agent 可以使用确定性规划，也可以启用模型规划，但计划只能从安全检查、知识库检索、答案生成、知识缺口创建和日志查询白名单中选择。

**原因：**

- 企业 AI 应用需要可审计、可解释、可权限控制。
- 每一步工具调用都有输入、输出、重试次数、耗时、状态和时间线，方便排查。
- 更适合面试展示“Agent 工程化”，而不是只展示不可控的模型输出。

**取舍：** 当前已支持进程内异步执行、持久化状态、幂等提交、协作式取消和失败重试，适合单实例演示与小规模部署。生产化仍需外部任务队列、任务租约、跨实例恢复、人工审批和更细粒度 ACL。

## ADR-005：保留本地抽取式回答与 OpenAI Chat Completions 兼容配置

**决策：** 默认未配置 API Key 时使用本地抽取式回答；配置环境变量后可接入 OpenAI Chat Completions 兼容接口。

回答生成前增加关键条件覆盖检查。系统从问题中提取关键短语，计算它们在 Top-K 标题和片段中的覆盖率；低于 `RAG_MIN_EVIDENCE_COVERAGE` 时不进入模型或本地拼接，而是返回可解释拒答，并记录覆盖率与缺失词。

**原因：**

- 面试演示不依赖外部网络和付费 Key。
- 简历项目可以稳定复现，不会因为模型服务不可用而无法演示。
- 仍保留真实大模型接入路径，体现 AI 应用扩展能力。

**取舍：** 本地抽取式回答能力有限，适合演示可信问答链路。真实生产效果需要接入更强模型、提示词模板、结构化输出和调用成本治理。

## ADR-006：发布治理作为工程能力的一部分

**决策：** 仓库包含 `.gitignore`、GitHub Actions、发布清单、最终验收报告、发布检查脚本、简历项目卡和面试官评分卡。

**原因：**

- GitHub 作品集不只看功能，还看可复现、可维护和边界意识。
- 发布检查脚本可以避免本地数据库、上传文件、Word 文档、隧道工具和密钥进入公开仓库。
- CI 和测试能证明项目不是“只在本机跑过一次”。

**取舍：** 这些治理文档不直接增加业务功能，但会显著提高项目在面试官眼中的工程可信度。

## ADR-007：默认安全与可解释降级

**决策：** 会话默认 12 小时过期，上传文件默认限制 10 MB，同源部署默认不开放 CORS；模型调用结果显式区分大模型生成、本地抽取和失败后的本地降级。

**原因：**

- 会话永不过期、无限制上传和通配跨域都会扩大演示系统暴露后的风险。
- 模型不可用时保留离线演示能力，但不能把本地回答和估算 Token 误报为供应商调用结果。
- 统一记录 `generation_mode`、`token_source` 和 `fallback_reason`，便于排障和成本分析。

**取舍：** 当前仍是轻量本地认证和文件校验。生产环境应继续增加 SSO、对象存储、恶意文件扫描、速率限制、模型网关和集中式可观测平台。

## ADR-008：使用版本化黄金数据集作为 RAG 回归门禁

**决策：** 将黄金用例和批准基线保存为仓库内 JSON，使用稳定键、版本号和 SHA-256 指纹识别数据集；每条用例声明执行角色，评测同时检查 Recall@K、MRR、答案、拒答、访问控制准确率的绝对阈值，以及相对同指纹、同 Top K 基线的最大回退。应用优先采用兼容的历史通过运行，首次运行回退到批准基线；CI 固定读取批准基线。CLI 与 API 共用门禁策略，CLI 失败返回非零退出码并在 GitHub Actions 上传 JSON 报告。

**原因：**

- 普通单元测试只能证明代码按预期执行，不能证明检索或拒答调整没有降低 AI 质量。
- 只在页面展示分数不会阻止退化进入主分支，门禁必须影响 CI 退出状态。
- 数据集指纹可以避免拿不同用例、不同 Top K 的结果进行无效比较。

**取舍：** 当前黄金集规模较小，适合仓库级确定性回归。生产环境仍需要分领域扩容、人工标注一致性和模型/Prompt 版本维度。

## ADR-009：容器保持单 Worker 并使用最小权限

**决策：** 提供非 root Docker 镜像和 Compose 交付，默认只绑定本机端口，数据写入命名卷，根文件系统只读，并固定一个 Uvicorn Worker。生产模式的空数据库必须通过环境变量提供强管理员密码，不创建公开演示账号。

**原因：**

- 干净机器可以用同一镜像复现依赖、前后端资源和启动行为。
- 当前 Agent 执行器的任务状态和线程池属于单进程，盲目增加 Worker 会造成任务所有权与恢复语义不一致。
- 非 root、能力裁剪、只读根文件系统和强密码引导可以消除作品集容器中常见的明显安全缺口。
- `/api/health/live` 与 `/api/health/ready` 分离，部署系统可以区分进程存活和 SQLite 可用。

**取舍：** 该方案提升单实例部署质量，但不等于高可用生产架构。横向扩容前必须迁移 PostgreSQL、对象存储和外部任务队列，再增加反向代理、SSO、集中日志与密钥托管。

## ADR-010：以 SQLite 为事实源接入可重建 pgvector 索引

**决策：** 保留 SQLite 作为业务事实源，把 pgvector 作为可选、可重建的向量检索投影。文档写入先提交 SQLite，再幂等同步外部向量；查询始终使用 SQLite 当前可访问的 `document_id` 过滤 pgvector 候选，并将候选关联回当前 SQLite 片段。外部索引不可用时可透明回退到 SQLite JSON，也可配置为就绪失败。

**原因：**

- 直接把全部 SQLite SQL、认证、审计和 Agent 状态同时迁移到 PostgreSQL，改动面大且与本阶段“消除向量全量扫描”的目标不匹配。
- 用当前允许的文档 ID 过滤，而不是信任外部索引中的权限副本，可以避免密级变更与索引延迟造成越权召回；最终回查 SQLite 可以排除已经删除或重建的孤儿片段。
- SQLite 与 PostgreSQL 不具备共享事务，把外部索引定义为可对账投影，比假装双写强一致更诚实、更容易恢复。
- 独立 Compose Profile 和真实数据库 CI 可以同时保留一键本地体验与可验证的生产组件接入。

**取舍：** 当前是混合架构，不等于完整 PostgreSQL 迁移。跨库同步是最终一致；默认 SQLite JSON 向量和 pgvector 故障后的本地降级仍会扫描可访问向量。生产大规模部署仍需迁移业务表，引入迁移工具、对象存储和外部任务队列。

## ADR-011：使用 FTS5 自动同步索引生成有界关键词候选

**决策：** 使用独立 SQLite FTS5 虚拟表保存应用预分词后的标题与正文，通过数据库触发器跟踪片段和文档标题变化。查询先由 FTS5 返回有限关键词候选，再与 pgvector 语义候选合并；最终只回载候选小集合执行原有字段加权 BM25、本地重排和实时 ACL 复核。

**原因：**

- 原实现会把全部可访问片段和 token JSON 加载到 Python，语料增长时内存、反序列化和 BM25 计算量线性上升。
- 复用应用中文分词后再交给 `unicode61`，可以保持 jieba 词项和单字回退，不依赖 SQLite 自带中文分词能力。
- 触发器覆盖上传、重索引、删除、种子脚本和直接数据库写入，比只在 API 路由中手动同步更不容易遗漏。
- FTS 查询和最终回载都关联当前文档权限，索引不承担授权事实，密级变化不需要重建索引。

**取舍：** FTS5 不可用时会显式降级为全量 BM25，以正确性换性能；SQLite JSON 向量模式仍保留本地全量向量扫描。大规模多实例部署仍应迁移统一业务数据库和检索服务。

## ADR-012：统一模型网关只重试可恢复故障

**决策：** 问答生成、Embedding 和 Agent Planner 统一通过轻量模型网关调用 OpenAI-compatible 服务。网关只重试超时、网络错误、429 和可恢复 5xx，采用有界指数退避并尊重受上限约束的 `Retry-After`；认证、参数和非法响应错误立即失败。连续可恢复故障按供应商主机触发进程内熔断，问答与 Planner 使用现有确定性降级路径。

**原因：**

- 外部模型服务会出现短暂限流、超时和 5xx，单次失败不应直接破坏完整业务请求。
- 401、403 或参数错误通常无法通过重试恢复，重复调用只会增加延迟、费用和供应商压力。
- 问答、Embedding 和 Planner 分别实现请求逻辑会产生不同的错误语义和配置，难以排查。
- 尝试次数、总延迟、HTTP 状态和错误分类进入现有轨迹后，可以区分模型质量问题、供应商故障和本地降级。
- 响应体、尝试次数、超时和退避均有硬上限，避免错误配置放大故障。

**取舍：** 当前熔断和计数器是单进程状态，适合仓库的单 Worker 交付；它不会被描述为跨实例高可用网关。生产多实例应迁移到独立模型代理或 API Gateway，并接入集中 tracing、告警、预算和供应商路由。

## ADR-013：SQLite Schema 使用不可变版本迁移

**决策：** 将当前完整表结构固定为 `0001` 兼容基线，后续结构变化只能新增连续版本，不修改已应用历史。每个版本在 `BEGIN IMMEDIATE` 获取写锁后独立执行，完成外键检查并记录版本、名称、SHA-256 校验值、时间和耗时；启动和 readiness 同时验证当前版本、待执行版本、校验漂移与未来版本。

**原因：**

- 零散 `_ensure_column` 只能判断字段是否存在，无法回答哪些版本执行过、代码与数据库是否匹配。
- SQLite 同一时刻只能有一个写者，并发启动必须在锁内重新检查历史，才能避免重复迁移。
- DDL、数据转换和历史记录处于同一事务，故障注入时可以证明失败版本没有留下半成品。
- 不可变迁移加校验值可以阻止已经发布的 SQL 被静默改写，避免不同环境拥有相同版本号却不同结构。
- 独立 `status`、在线备份和 `upgrade` 命令让部署前检查和故障恢复可操作，而不只是写在设计文档里。

**取舍：** 迁移器只服务当前 SQLite 事实源，不管理可重建 pgvector 投影，也不提供高风险的通用自动降级。未来迁移 PostgreSQL 时会引入 SQLAlchemy/Alembic、部署锁和备份恢复演练，而不是扩张这套轻量实现。
