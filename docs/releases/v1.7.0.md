# v1.7.0 - Versioned Schema Migrations Release

`v1.7.0` 解决 SQLite 表结构长期依赖启动时零散字段补丁、无法证明旧库升级顺序和失败原子性的问题。当前版本建立了可追踪、可校验、可回滚当前步骤的 Schema 演进机制，并用真实旧结构和故障注入测试验证升级行为。

## 核心变化

- 使用连续版本迁移替代 `init_db()` 中 60 多个 `_ensure_column` 调用，完整基线固定为不可变 `0001` 迁移。
- 新增 `schema_migrations` 历史表，记录版本、名称、SHA-256 校验值、应用时间与耗时。
- 每个版本在独立事务中执行，升级后运行外键检查；失败时回滚 DDL、数据和迁移历史。
- 使用 `BEGIN IMMEDIATE` 串行化同一 SQLite 文件上的并发升级，并在锁内重新检查版本，保证幂等。
- 已应用迁移被修改或数据库来自更高版本时拒绝启动，避免带着未知 Schema 继续运行。
- 新增 `status`、在线一致性 `backup` 和 `upgrade` CLI；备份完成后执行 SQLite 完整性检查且不覆盖已有文件。
- `/api/health/ready` 返回当前和期望 Schema 版本，未对齐时使用通用 503 响应阻止接流量。

## 验证证据

- 全量回归：170 项 pytest 通过，2 项真实 pgvector PostgreSQL 测试在本地按设计跳过并由 CI 专用任务执行。
- 8 项迁移专项测试覆盖全新库、旧数据保留、重复执行、校验漂移、未来版本、失败回滚、双连接并发和在线备份。
- 12 条角色化 RAG 黄金用例全部通过，Recall@K、MRR、答案、拒答与访问控制准确率均为 100%。
- 在真实 `v1.6.0` 运行数据库副本上完成 `uninitialized -> ready` 升级，并核对业务表行数不变。

## 运维入口

```powershell
cd backend
python -m app.migration_cli status
python -m app.migration_cli backup
python -m app.migration_cli upgrade
```

完整升级、恢复和新增迁移规则见 [数据库迁移运维指南](../database_migrations.md)，设计取舍见 [ADR-013](../architecture_decisions.md)。

## 诚实边界

当前迁移器只管理 SQLite 业务事实源，不迁移可重建的 pgvector 投影，也不提供通用自动降级。未来把业务库迁移到 PostgreSQL 时，应使用 SQLAlchemy/Alembic、独立数据库账号、部署锁、备份快照和恢复演练，不会把当前轻量迁移器描述为完整多实例生产方案。
